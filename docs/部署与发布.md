# 部署、发布包与证书

> 从 CLAUDE.md 原样搬出（2026-10-20 精简时）。这里是排查经过、现象和测量数据；CLAUDE.md 里只留现在成立的结论。
> 文中「见『某某』一节」指原 CLAUDE.md 的小节，现在分在 docs/ 下的各个文件里，按标题搜即可。

## 部署

```bash
zsh tools/setup.sh              # 只跑一次：这台电视、这台电脑、证书
node tools/collect.mjs          # 终端 1，一直开着
zsh tools/deploy.sh             # 终端 2：检查、签名、安装、启动（约 15 秒）
zsh tools/deploy.sh --selftest  # 同上，但构建会自己走一遍全流程并上报
zsh tools/deploy.sh --tokenswap # 只测「播放中 web 令牌被拒」那条路，约一分钟，见「强令牌这条路三处提速」
```

**电视地址、型号、DUID、网卡不再写死在脚本里** —— `setup.sh` 把它们写进
`~/.bilibili-tizen.conf`（仓库外，权限 600），`deploy.sh` 每次读取，环境变量可以
临时覆盖（`BILI_TV_IP=… zsh tools/deploy.sh`）。**这句覆盖 2026-10-20 才真的成立**：此前
配置文件在环境变量之后 `source`，把它们全盖掉 —— `BILI_PROFILE=… zsh tools/deploy.sh` 照样用
文件里的签名档签名、装上、启动。

**自己在 Tizen Studio 证书管理器里建了签名档的人**，在配置文件里写 `BILI_PROFILE="<名字>"`
就行，`deploy.sh` 不再要 `~/.bilibili-tizen-cert-password`（2026-10-20 起，只有签名档要从
`setup.sh` 签的证书现建时才读它；缺什么会逐个列出来）。issue #4 那位此前只能把建签名档那段
整个注释掉。三星 CA 证书不在 `setup.sh` 签的东西里，在证书管理器的
`org.tizen.common.cert_*.jar` 的 `res/ca/` 下（这台 Mac 是 08-01 解到 `~/tizen-studio-data/samsung-ca` 的）。这么改是为了公开发布：原来的形态
要求陌生人去改三个文件里的常量，而其中任何一个改错都表现成别的故障 —— 主机地址错
是 sdb 静默超时，DUID 错是证书签得出来、装不上去。

`tools/check.sh`（`deploy.sh` 和 `release.sh` 共用，2026-10-17 从 `deploy.sh` 里抽出来）
开头先问两样新 clone 不带的东西（2026-10-23 起，issue #4）：`node:sqlite`（`diag-verify` 拿它冒充 D1，Node 22.13 起不用开关；
18.20、20.19、22.12 都在那一步崩出堆栈）和 `tools/` 的依赖（`mpd-verify` 用 `fast-xml-parser`；原来在 `devDependencies`，
`--omit=dev` 装会漏掉，现在挪进了 `dependencies`）。仓库里原来没有任何一步跑 `npm install`，现在 `setup.sh` 跑一次。接着
对每个文件跑 `node --check`，然后依次跑 `tools/lint.mjs`、
`tools/md5-verify.mjs`、`tools/accounts-verify.mjs`、`tools/mpd-verify.mjs`、
`tools/mirrors-verify.mjs`，
**任何一个失败就拒绝安装** —— 光靠语法检查曾经放过一个「按确认键什么都不发生」
的构建。

`deploy.sh` 会改写 `app/js/config.js` 里的 `REPORT_TO`，让电视知道诊断往哪发。
它还从构建产物里推导包文件名，而不是写死：`tizen` 按 `config.xml` 里的 `<name>`
命名 wgt，有一次改了应用名，安装器一直在推旧包而启动步骤欢快地起了上一个版本
—— 表现和「新代码毫无效果」一模一样。

结果通过 HTTP 回来，因为零售机上 `dlog` 是关的：应用把错误 POST 到 8099 端口的
`collect.mjs`。收集器没开的话，上报静默失败。`tizen debug` 那个 Web Inspector
是兜底手段，用在应用还没来得及上报任何东西就死掉的场合，比如加载期的语法错误。

**应用编号是 `BiliTvApp0.Bilibili`（2026-10-02 起）。** 之前一直是探测版留下来的 `BiLiSpiKe0.BiliSpike`，
2026-10-01 另一个项目的会话清理「spike」应用时按名字把正式版当探测版卸了。改编号在电视看来是另一个应用：
旧的要单独卸（`tizen uninstall -p BiLiSpiKe0.BiliSpike -t <设备>`，或者电视上长按图标删），应用里存的东西
（扫码登录、进度、自更新落盘的版本）不跟过来。`~/.bilibili-tizen.conf` 里的 `BILI_APP_ID` 同时改了。
签名档 / 证书目录仍叫 `BiliSpike`，那是证书的名字，和应用编号无关，没动。

### 发布包（2026-10-17 起）

```bash
zsh tools/release.sh   # → dist/bilibili-tizen-<config.xml 的 version>.wgt
```

给陌生人用 [Apps2Samsung](https://github.com/Apps2Samsung/Apps2Samsung) 装的包，不碰电视。

- **绝不能用 `SamsungBili` 签。** 那套证书里有三星账号邮箱、真实姓名和公司、客厅这台电视的
  DUID，签进 `signature1.xml` / `author-signature.xml` 就等于公开发布 —— 用 openssl 读一个
  部署包就看得到。发布用 `BiliRelease` 签名档：一次性的作者证书 `CN=bilibili-tizen`
  （`~/tizen-studio-data/keystore/author/bilibili-tizen-release.p12`，密码在
  `~/.bilibili-tizen-release-password`，首次运行自动生成）加 SDK 自带的测试分发证书 ——
  和 TizenTube 发布包的签名形态一模一样。
- 这套签名装不上任何一台 2023+ 的电视，**也不需要装得上**：Apps2Samsung 安装时用用户自己的
  三星证书重签（`WgtInstaller` → `ResignAsync`），按 `config.xml` 里的权限自动选 Public /
  Partner，我们的权限全是 Public 级。
- **取自 `git archive HEAD`**，`app/` 有未提交改动就拒绝 —— `app/` 里常年躺着上次部署的
  wgt 和签名文件，直接打包目录会把它们带进去。
- **打完包读回来验，不信前面的步骤**：文件清单必须正好是 `git ls-files app` 加两个签名文件，
  `REPORT_TO` 为空、`SELFTEST` 为 false，签名里不许有三星签发的、带 `deviceid=` 或
  `emailAddress` 的证书。拿一个旧部署包喂过，全部报出来。
- **别把签名档里的密码改成明文。** `deploy.sh` 建 `SamsungBili` 时会把 `*.pwd` 改写成明文；
  `release.sh` 照做之后 `tizen package` 停在 `Author password:`，然后 NullPointerException。
  这台 Mac 上那些 `.pwd` 文件根本不在磁盘上，路径只是 CLI 存密码用的键；本机三个能用的签名档
  （包括 `SamsungBili`）现在都是没改写的形态。
- 发布包没有诊断通道，`Updater.probe` 也就不跑（它只在上报通过之后才跑）。
- **截至 2026-10-17 还没有用 Apps2Samsung 在电视上实装过这个包。** 装过之后改掉这一条。

## 证书

放在 `~/tizen-studio-data/SamsungCertificate/BiliSpike/`，**故意放在仓库外**，
因为里面含私钥。签名档名为 `SamsungBili`，密码从 `~/.bilibili-tizen-cert-password`
读，同样在仓库外。**分发证书大约 2027-08 过期。**

要重新签发，`node tools/samsung-cert.mjs` 会打开三星账号登录、捕获 OAuth 回调、
向 `svdca.samsungqbe.com` 提交 CSR。不需要 Eclipse、不需要 sudo、不需要 Tizen
的证书 GUI。

那个脚本的注释里埋着一个坑，值得再说一遍：OAuth 回调里的 `code` 参数**不是**
授权码。三星把整个 token 载荷以 JSON 塞进了它。拿去
`api.samsungosp.com/v2/license/security/authorizeToken` 换取会从任何普通网络得到
`403 ACF_0403 [AllowList]`，读起来像权限问题，其实是走错了路 —— 直接解析那段
JSON 就行。
